# RomStop: the RomM add-on

It reads `device/index.json` published by the RomStop site (`format: 1`). The site, its hack data and the code that writes the index live in a separate, private repo; this repo only reads the index. Moved here from that repo on 2026-10-31. User-facing behavior is described in `romm/README.md`; this file covers how it is built and what to keep in sync.

## The device index (contract)

The site build writes `<site>/device/index.json` with this shape. Any change to it is made in both repos together: a PR in the site repo that writes the new field, and a PR here that reads it.

```
{ format: 1, generated, consoles: { <id>: {name, short, extensions, colors} },
  hacks: [ { id, title, console, baseGame, baseRom, authors, type, genre, version, released, updated, summary, description,
             rating, page, links, patches[{path,name,format,size,crc32,sourceUrl,sourceLabel,version}], noMirror,
             downloadUrl, versions, ratings, favs, favsUrl, features, tags, patchFormat, screenshots, titleScreen,
             language, patchNotes, downloads, compatibility{...,summary,names}, play{esde,batocera,emulatorjs},
             install{...,label,needs,steps,emulator}, mario{difficulty,length,types},
             achievements{id,count?,points?,url,via} } ] }
```

- Patch `path`s are relative to the site root, or absolute R2 URLs. `noMirror` hacks list no patches.
- Any field change or removal must be checked against `romm/overlay/backend/handler/romshelf/index.py` (`_prepare`, `_absolute`) and the RomM frontend types in `romm/overlay/frontend/src/services/api/romshelf.ts`. Adding optional fields is safe; bump `INDEX_FORMAT` (romstop.py) together with the site's index format for breaking changes.

## RomM add-on (`romm/`)

RomM has no plugin system, so RomStop is an overlay on RomM source pinned to `romm/ROMM_VERSION` (5.4.1).

- `romm/overlay/` holds new files copied over a RomM checkout; `romm/romm.patch` holds edits to eleven upstream files (`backend/main.py` registers the router under `/api`; `backend/config/config_manager.py` adds a `<games dir>/Hacks/{game}` layout to every platform without wildcard levels (`with_hacks_folder`), so files in a `Hacks` folder scan as separate games instead of one multi-file game named Hacks; frontend router, route names, nav destinations, `GameDetails.vue` for the tab, the Settings sidebar and user menu for Send with FTP, `AssetActions.vue` for the Send with FTP button on own save/state rows, e2e pages). `romm/apply.sh <checkout>` applies both; `romm/export-from-tree.sh <checkout>` regenerates them after editing in a checkout. Do not hand-edit `romm.patch` hunks.
- Image: `romm/Dockerfile` clones RomM at `ROMM_VERSION`, applies the overlay, runs the frontend `typecheck` + `build`, then copies the patched backend files and built frontend onto `rommapp/romm:<version>`. Published as `ghcr.io/itsdinkd/romstop-romm:{latest,<version>}` on pushes to `main` that touch `romm/**` (`romm-image.yml`; PRs build and smoke-test against MariaDB).
- Backend API (`endpoints/romshelf.py`, prefix `/api/romshelf`, scopes `ROMS_READ`/`ROMS_WRITE`): `GET /status`, `POST /refresh`, `GET /hacks`, `GET /hacks/{id}`, `GET /roms/{rom_id}` (hacks for a game with match info), `POST /install`, `GET /installs/{record_id}`, `GET /counts/{hack_id}` (this RomM's download/play counts); saved hacks (`ROMS_USER_READ`/`ROMS_USER_WRITE`): `GET /saved`, `PUT /saved/{hack_id}`, `DELETE /saved/{hack_id}` (the list and hack responses also carry `saved`); save import (`ROMS_READ` + `ASSETS_READ`, read-only): `GET /saves/options` (systems, games, emulator names), `POST /saves/plan`; Send with FTP: `GET /ftp/status` (`ROMS_READ`), `GET`/`PUT /ftp/settings` (`{enabled, default, targets: [...]}`) and `POST /ftp/test` (one target's form) (admins only, `assert_admin`), `POST /ftp/send` (`ROMS_WRITE`, body `{install_id}` or `{rom_id}`, plus `target`, returns a job), `GET /ftp/jobs/{id}`, saves and states (`ASSETS_READ`, the caller's own or a public save; the game must be visible): `POST /ftp/save/plan` and `POST /ftp/save/send` (body `{type: save|state, id, folder?, file_name?, replace?, target?}`; a file already there is a 409 `exists` unless `replace`), `GET`/`DELETE /ftp/save-paths` (the folders this user typed in); `POST /install` takes `send_ftp` and `ftp_target`, and install records carry `ftp_job`.
- Handler modules (`handler/romshelf/`):
  - `index.py`: downloads and caches the device index (`ROMSTOP_SITE_URL`, `ROMSTOP_INDEX_URL`, `ROMSTOP_INDEX_TTL_SECONDS`, default **600 s**, conditional ETag/Last-Modified requests; cache under RomM resources `romshelf/`).
  - `library.py` + `matching.py`: hash the library in the background (headerless CRC/SHA, cached) and match hacks to ROMs: `MatchLevel` exact (checksum) / likely (name, game and region) / wrong_version / none; `PLATFORM_CONSOLE` maps RomM platform slugs to RomStop console ids.
  - `patch_source.py`: download the patch (URL list from `patch_urls`: version's mirrored patches first, preferring BPS/UPS, then the source `downloadUrl` unless `manual_only`), unpack zip/7z/rar (`/usr/bin/7zz`, `bsdtar`), refuse any archive holding a program (`unsafe`), pick among multiple patches (`NeedsChoice`), or accept a user-uploaded file (`browser_download` code when the server cannot fetch).
  - `installs.py`: strips headers, applies the patch with RomM's `utils.rom_patcher.apply_patch`, saves `<Hack> (<region>) (v<ver>) [RomStop].<ext>` in the platform's games folder, or in its `Hacks` subfolder when the install asks for it (`hacks_folder`; created if missing; a copy already in either folder is replaced in place), scans it into the library and finalizes metadata (description, cover, screenshots, authors, release date, locked via `manual_metadata`), adds it to the "RomStop" collection, and records installs in `installs.json` (file-locked). `modpatch.py` + `install_mod` handle Wii Riivolution and Vita rePatch installs (Python twin of `src/lib/modpatch`).
  - `community.py`: RomStop's own ratings, favs and download counts, from the site's `GET /api/community` (every `ROMSTOP_COMMUNITY_TTL_SECONDS`, default 600 s; Refresh fetches again; `ROMSTOP_COMMUNITY_URL` overrides the address). The endpoints fold them into each hack like the site does: a "RomStop" row in `ratings`, the headline `rating` re-averaged by count, RomStop favs added to `favs`, site downloads plus RomM installs added to `downloads` (the scraped values are kept under `_scraped`, which `hack_payload` leaves out). Each install is also reported to the site (`POST /api/community {hack, install: true, client}`, in the background; `client` is a random id in `romshelf/client_id`, counted once per RomM per hack), so the site's download counter includes RomM. `ROMSTOP_SHARE_INSTALLS=0` turns reporting off. If the site can't be reached, the scraped numbers show.
  - `counters.py`: counts for this RomM only (the HackCounters chips). Downloads: each successful install adds one in `romshelf/counts.sqlite` (a failure to count never fails the install). Plays: RomM's own `play_sessions` rows for the ROMs installed from the hack (`installs.json`).
  - `saved.py`: Save Rom Hack, per RomM user id, in `romshelf/saved.sqlite` (owner's choice, 2026-10-30: kept on the RomM server like the counts, nothing extra runs on the owner's PC). Ids the index later drops stay saved and are simply not listed.
  - `ftp.py` (stdlib `ftplib` + `cryptography`): Send with FTP (owner's request, 2026-11-13: generic FTP, with the PS5 as a preset, not hardcoded). Several targets (devices) set by an admin in `romshelf/ftp.json` (owner's request, 2026-11-14: e.g. a PS5 plus another device): `{version: 2, enabled, default, targets: [...]}`, each target with its own id, server, folders and saves settings; a file from the first release (one target's keys at the top level) reads as one target with id `main`. Every send takes a target id (empty = the default); `status()` lists the ready targets, default first, and jobs record `target_id` (a second click joins a running send of the same file to the same target). Mode 600; each password Fernet-encrypted with a key derived from `ROMM_AUTH_SECRET_KEY`, never returned, kept when the form leaves it blank; a changed secret key asks for it again). A game goes to `<base path>/<folder>/[<Hacks folder>/]<file>`: folder = the admin's per-platform mapping, else the RomM platform folder (`fs_slug`); the Hacks folder `match`es RomM (the ROM's `fs_path` ends in `ROMSTOP_HACKS_FOLDER`), or is `always`/`never`. Folder games keep their layout. Existing files are replaced or skipped. `PRESETS` (`ps5-retroarch`: port 1337 for etaHEN's FTP, 2121 for ftpsrv, base `/data/homebrew/PPSA99169/content`, RetroArch's content folder on the owner's PS5, 2026-11-14; `retroarch`) only fill the form. Jobs live in `romshelf/ftp.sqlite` (`running` / `done` / `failed`, keyed by the library file in `source` so a second click joins the send under way; one silent for 10 min reads as failed). Sends run in a daemon thread in RomM's web process. `ftp_send.py` (RomM side) works on the library file, never on the scan (owner's rule, 2026-11-14: Install and Send with FTP are independent, and sending must not wait for RomM's scan): `POST /install` with `send_ftp` starts the send as soon as the patched file is written (`send_install_or_record_failure`; a send that can't start is a failed job with its reason and never fails the install), and the Send with FTP button sends by install id (`send_install`, using the record's `fs_path`/`fs_name`/`platform_fs_slug`) or by ROM id (`send_rom`). Saves and states (owner's request, 2026-11-14): `ftp_send.save_plan` / `send_save` send one save or state to the settings' `saves_path` / `states_path` (unset = pick a folder each time), with subfolders per `saves_layout` (`flat`, `core` = RetroArch core folder from `RETROARCH_DIR_BY_ROMM_EMULATOR`, `content` = the game's console folder on the device, `core_content`), or to a folder the user types in, remembered per user in the `save_paths` table of `ftp.sqlite`. The file is renamed to `<ROM file stem><ending>` (RomM's ` [date_time]` tag dropped; `device_save_name`), since RetroArch finds saves by the game's name. A file already there is never overwritten silently: the send is refused unless the user confirms, and then `send` renames the old one to `<name>.bak-<YYYYmmdd-HHMMSS>` before writing (`Upload.backup`; a failed rename stops the send). The PS5 preset's `/data/homebrew/PPSA99169/saves` and `/states` are unverified.
  - `archives.py`: reads/extracts ROMs from zip/7z/rar for hashing and patching.
  - `saves.py` (stdlib only): the save import planner. Classifies a file (save, state, state screenshot, shared memory card, folder save), matches it to a RomM ROM (exact file name, case, loose name, device ROM CRC32), picks the emulator (RetroArch `saves|states/<core>/` folder via RomM's `handler/sync/retroarch/emulator_names.py`, standalone emulator folder, RetroArch `.lpl` playlists, ES-DE gamelist `altemulator` / `alternativeEmulator` and `es_systems.xml` default), names it `<ROM fs_name_no_ext><suffix>` like RomM's Cloud Sync, and checks it against the user's saves/states (MD5 = RomM's `content_hash`). A taken name with different content is a `conflict`, offered under RomM's version tag (` [YYYY-MM-DD_HH-MM-SS]`); it never overwrites.
- Frontend (Vue, RomM "v2" UI): `InstallPanel` (used by the RomStop page and the game page tab) has the "Save to a Hacks folder" checkbox, remembered per user in local storage (`romstop.install.hacksFolder`) and hidden when replacing an install. While Send with FTP is on (`ftp.ts` `useFtpStatus`, fetched once per page load), it also shows `SendFtpButton` next to Install for an installed hack (polls the job, snackbar with the device path) and a "Send with FTP after installing" checkbox (`romstop.install.sendFtp`), sent with the install as `send_ftp`; with several devices a picker next to it (`romstop.install.ftpTarget`, sent as `ftp_target`), the Send with FTP button opens a menu of devices, and the save dialog has a Device select; the button appears as soon as an install exists (before the scan), sends by install id, and follows the record's `ftp_job` (also after a reload, while it is running). Test connection warns when none of the library's platform folders is in the base path. Settings > Send with FTP (`views/Romshelf/FtpSettings.vue`, route `romstop-ftp`, scope `users.write`, sidebar and user menu entries for admins): a Devices list (add, remove, make default; the sections below edit the selected device), then per device: name, preset, server, Test connection (lists the base path's folders and marks which platforms already have one), per-platform folders, Hacks folder mode, saves and states folders and their subfolder layout. `SendSaveFtpButton` (in RomM's `AssetActions`, after download, own saves/states only, while Send with FTP is on) opens a dialog: the settings folder in italics with the detected console and emulator, or another folder with a dropdown of remembered ones ("Type to add path…"), the device file name (editable), an "already there" check that turns Send into Replace and send. `views/Romshelf/RomshelfIndex.vue` (top-bar page), `RomshelfHack.vue` (the base game's name links to the best library match, `matches[0]`, via `HackDetails`' `romLink`), `components/Romshelf/*` (`RollButton` + `RollDialog` + `roll.ts`: "Roll a Rom Hack" on the index page, a case-opening reel that lands on a random hack that isn't installed, has a fetchable patch and an exact/likely library ROM, then opens it with `?rolled=1`; only then does the hack page show Re-roll; `HackCounters`, `SaveHackButton` (bookmark on index cards and list rows, button on the hack page; the index's Saved toggle, `?saved=1`, narrows the Show filters and their counts), `RomshelfTab`, `HackRow`, `HackDetails`, `InstallPanel`, `ChangelogDialog`, `ScreenshotGallery`, `MarioSpecifics` + `mario.ts` (SMW Central's Difficulty/Length/Mario Type card on the hack details), RetroAchievements (index field `achievements`, passed through `_SUMMARY_FIELDS`: a trophy with the achievement count on index cards and list rows, an "Achievements (n)" toggle next to Saved on the index, `?ra=1`, that narrows the Show filters like Saved does, and a RetroAchievements row in `HackDetails` linking to the set), `RichText`, `MatchBadge`, `compat.ts`, `markdown.ts`), API client `services/api/romshelf.ts`.
- Save import UI: `SaveImportDialog.vue` (opened from the RomStop page, `?import=saves`) + `saveScan.ts`. Folders are read in the browser with `<input webkitdirectory>` (works over plain-HTTP LAN addresses, unlike the File System Access API); MD5 via `spark-md5` and CRC32 in JS because `crypto.subtle` needs a secure context. The dialog plans again right before uploading and uploads through RomM's own `POST /api/saves` and `/api/states` (no `overwrite`, no `slot`, no `autocleanup`), so nothing in RomM is deleted or replaced and nothing on the device is written. Not imported yet: shared memory cards (RomM's `/api/memory-cards` takes only its streaming broker's zip layout) and folder saves.
- Tests: `romm/tests/` (`test_matching`, `test_archives`, `test_modpatch`, `test_patch_source`, `test_counters`, `test_community`, `test_saved`, `test_saves`, `test_ftp`); run `python3 -m unittest discover romm/tests` (94 tests; skipped: 1 when 7-Zip is not installed, 1 without `pyftpdlib`, the real-FTP-server test; `test_ftp` needs `cryptography`, CI installs both). The frontend and the image build are only verified in CI.
- Behavior to preserve: RomM never sends the user to an outside site for a patch (server fetches it; manual drop is the fallback); installed hacks get a working EmulatorJS core from `hack.play.emulatorjs` unless the user chose one; update badges and a version picker for installed hacks.

## Windows 11 installer (`romm/windows/`)

- `Install-RomM.ps1`: enables WSL2 (restart code 3010, resumes by itself via a RunOnce registry entry / `-Resume`), installs Docker Desktop, writes a docker-compose project (`RomM` + `mariadb:11`) and `.env` (keeps existing passwords on re-run, so it doubles as repair/upgrade), pulls `ghcr.io/itsdinkd/romstop-romm:latest`, starts RomM (default `http://localhost:8080`) and creates shortcuts. Options: `-LibraryDir`, `-Port`, `-ScanWorkers` (`SCAN_WORKERS`, default 8), `-SettingsFile` (JSON, deleted after reading), `-DryRun`.
- `Update-RomM.ps1` (pulls the newest image, or rebuilds `romstop-romm:local` from the repo), `Uninstall-RomM.ps1` (`-RemoveData`; never touches ROMs), `RomM-RomStop.iss` (Inno Setup wrapper, builds `RomM-RomStop-Setup.exe` in CI). Published by `release.yml` as a GitHub release asset.
- Constraint: scripts must run in Windows PowerShell 5.1, and native programs that write to stderr must not abort the script (`Invoke-Native`; CI tests this). CI lints with PSScriptAnalyzer and dry-runs the installer.
- The installer is exercised only in CI; real-machine behavior is unverified from this repo.

## Names kept from before the rename

The project was called Romshelf. Internal names were kept so existing installs keep working: the `/api/romshelf` endpoints, the `handler/romshelf/` modules and their `romshelf/` data folder in RomM resources, Vue component names, and the `ROMSHELF_*` environment variables (still read when `ROMSTOP_*` are unset). Anything a user sees says RomStop. Hacks installed before the rename are tagged `[Romshelf]` and stay in a "Romshelf" collection, which new installs keep using.

The ES-DE / Knulli tool (`device/`) was removed for now on 2026-10-31; see the repo history.
